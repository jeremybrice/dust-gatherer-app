# Dust Gatherer

A single-user web app for tracking resale inventory — thrift store find through to final sale.
Deployed at https://dust-gatherer-app.netlify.app.

Converted from a native Android app (Kotlin/Compose/Room). The Android source is gone from
the tree but remains in git history before `46d7f5f` — it is the reference for any behaviour
question, and the only specification of the backup format.

**Read `PLAN-pwa-conversion.md`** for the architecture and the reasoning behind it.

## Stack

Next.js 15 (App Router) + React 18 · TypeScript · Netlify · Netlify DB (Neon Postgres) via
Drizzle · Netlify Blobs for images · single passphrase in an env var, `jose` session cookie.

## Current state

The migration is done. **Production holds the real inventory — 208 items with photos** —
imported from the Android backup and rendering with correct status badges and money.

Working end to end: sign-in, command-center Home (this-month profit, shelf
value, posted-waiting, stale, oldest/recent strips), inventory search and
filters, item CRUD with camera capture, settings hub, backup export, the
database, image storage, and the import pipeline. Also: installable PWA
(manifest, icons, service worker, Settings install instructions),
English / Українська via Settings (cookie `dg-lang`), and a per-device colour
theme (cookie `dg-theme`, `src/lib/theme.ts`, Settings → Colours): nine
mix-and-match colours (separate light and dark backgrounds) plus
System/Light/Dark, resolved through semantic CSS tokens in `globals.css`.
Installed-app chrome (`theme-color` / manifest) follows the page background,
not the accent. Inventory has two chip rows (status vs. views), dates
on scheduled/posted rows, and a 50/100/all page size (`?limit=`).

Not built yet, roughly in intended order:

1. Calendar / Schedule
2. Category and site management UI
3. Quick Posted/Sold actions from the list ("slides"; awaiting her clarification)
4. AI description suggestion from the photo (style and occasion)
5. Bulk select — never implemented on Android either

Analytics must reproduce the **current** Android behaviour, which `PLAN.md` redesigned:
`inventoryValue = totalSpent - COGS`, `salesProfit = totalRevenue - COGS`.

## Backups exist but only when you run them

Export now ships from `/settings/export` as a v2 ZIP the app's own importer accepts. The risk
is now discipline, not capability: anything changed since the last export is still unbacked,
and `netlify database reset` still destroys everything since that export.

**`netlify database reset` destroys the inventory.** It sits in the CLI's own examples list
next to harmless commands.

## Traps

Every one of these cost a deploy cycle. They are not hypothetical.

**Test the driver you actually deploy.** The original client used `drizzle-orm/netlify-db`,
whose Neon HTTP transport reaches the Netlify runtime *missing a method it defines on itself*,
so every query failed in production while 37 tests passed locally — because the tests drove
`drizzle-orm/pglite`. `src/lib/db.ts` now uses `drizzle-orm/node-postgres`, and
`tests/integration/driver.test.ts` exercises that exact module over a real TCP socket. Keep it
that way.

**Port against the JSON, not the Kotlin.** `kotlinx.serialization` omits properties equal to
their default, because the Android exporter leaves `encodeDefaults` false. `ExportManifest.version`
therefore never appears in a real backup, nor does an item's empty `site`, nor empty
`categories`/`sites` lists. Reading the data class instead of its output rejected every genuine
archive — and the fixtures, written from the same misreading, agreed with the bug.

**Migrations apply automatically on deploy.** `npm run db:migrate` targets the *local* dev
database. So does `netlify database status` — its "Pending (1)" is about local state and says
nothing about production. To check production, look at the Database tab's table browser.

**The importer writes explicit row ids**, so `inventory_items.id` must stay
`GENERATED BY DEFAULT AS IDENTITY`, never `ALWAYS`, and the identity sequence must be advanced
afterwards (`resyncItemSequence`) or the next insert collides. Preserving ids is deliberate: it
makes re-importing the same archive idempotent instead of duplicating the inventory.

**Middleware runs on the edge; route handlers run on Node.** Anything middleware imports must
use Web Crypto only — `src/lib/session.ts` obeys this, which is why the passphrase comparison
lives in `/api/login` instead. Importing `node:crypto` into that path breaks the build.

**Security headers belong in `src/middleware.ts`, not `netlify.toml`.** Netlify applies config
headers *after* middleware, so headers declared there silently win.

**Keep PWA assets public in the middleware matcher.** A redirected `/sw.js` fails service
worker registration and quietly makes the app non-installable.

**Only `--user-*` variables go inline on `<html>`.** `layout.tsx` writes the theme cookie's
colours as `--user-accent`, `--user-bg`, ...; `globals.css` resolves `--accent`, `--bg`, ... from
them with defaults. Inline `--bg` itself would beat the dark-mode stylesheet rule and the phone's
dark setting would stop working.

**Money is `numeric(10,2)` with `mode: "number"`**; the four `LocalDate` fields are `date`, not
`timestamptz`, or dates shift across timezone boundaries. `status` and `profit` are derived in
`src/lib/itemStatus.ts` and must never become columns.

**Netlify Blobs cannot run locally at all** — it needs a Netlify runtime context. Upload and
serving are now proven in production by the import, but any *new* Blobs work is unverifiable
until deployed. This is the same category of gap that caused the driver outage; treat it that
way.

## Deploying

Push to `main` — Netlify builds and applies pending migrations. **Deploy from the Netlify UI
or by pushing, never `netlify deploy --prod` locally**: that builds on your machine and bakes
macOS-specific `sharp` binaries into Linux functions.

## Local development limits

`npm run dev` gives you the UI and sign-in. The database needs `NETLIFY_DB_URL` in
`.env.local`; Netlify Blobs will not work at all, so photo upload and the import's image phase
are deploy-only.
